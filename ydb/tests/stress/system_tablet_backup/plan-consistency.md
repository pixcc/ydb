# Тестирование консистентности после восстановления системных таблеток

Цель: локально воспроизвести продовый профиль нагрузки на Hive / BSController /
SchemeShard, восстановить одну из таблеток из **устаревшей** резервной копии,
найти классы расхождений между таблетками и научиться их обходить.

### Выводы

1. **Это NBS-кластер** (`TTxBlockStoreConfigResult` 1.19/s). Локально роль
   волюма играет обычная таблица — набор задействованных tx в SS/Hive/BSC тот же.
2. **Цепочка сходится по числам:** SS `TxCreateTabletReply` 1.97/s ≈ Hive
   `TxCreateTablet` 2.06/s. Это и есть сквозная ссылка, которая рвётся при
   рассинхроне бэкапов.
3. `TxStartTablet` (8.2/s) вчетверо больше `TxCreateTablet` → нужен отдельный
   генератор рестартов, иначе Hive не переписывает `KnownGeneration`
   и `TabletChannelGen`.

### ⚠️ Оговорка по данным

`Local` шлёт один `TEvTabletMetrics` на узел не чаще, чем раз в
`TABLET_METRICS_BATCH_INTERVAL = 5s` (`ydb/core/mind/local.cpp:107,617`,
константа, конфигом не управляется). 3997 tx/s → ~20 000 отправителей, что для
одного Hive нереалистично. **Вероятно, ряд просуммирован по всем Hive кластера
(root + tenant) или по хостам.** Перед точной калибровкой стоит перевыгрузить
ряды с фильтром по `tablet_id` корневого Hive. На структуру нагрузки это не
влияет — меняется только масштаб.

### Чекер

Читает состояние **из снапшотов резервных копий** — это готовый NDJSON-дамп
каждой таблицы локальной БД. Не нужен ни доступ к живому кластеру, ни новые
ручки мониторинга. Поверх снапшота применяется `changelog.json`, иначе всё
созданное после последнего снапшота выглядело бы потерянным.

Инварианты:

| id | утверждение | ломается при |
|---|---|---|
| `I1` | шард из SS известен Hive под тем же владельцем | откате Hive |
| `I2` | у Hive нет таблеток, о которых SS не знает | откате SS |
| `I3` | группы из каналов Hive существуют в BSC | откате BSC |
| **`I4`** | Hive не выдаст повторно используемый TabletId | **откате Hive** |
| **`I5`** | BSC не выдаст повторно используемый GroupId | **откате BSC** |
| **`I6`** | SS не выдаст повторно используемый ShardIdx | **откате SS** |
| `I7` | слоты BSC ссылаются на существующие группы и диски | откате BSC |
| `I8` | всё созданное по леджеру живо в SS | любом откате |
| `I9` | диапазоны последовательностей Hive корректны | ручной правке |
| `I10` | счётчики SS выше собственных таблиц | ручной правке |
| `I11` | насколько состояния разъехались по времени | — (контекст) |
| `I12` | аллокаторы выше всех id из леджера | откате Hive **и** SS |
| `I13` | changelog не обрезан | сбое во время записи |
| `I14` | датировка состояний по леджеру (точная) | — (контекст) |
| **`I15`** | Hive не выдаст id, принадлежащий тенантному Hive | **откате Hive** |
| `I16` | у каждой базы её таблетки известны Hive | откате Hive |
| `I17` | нет баз, о которых забыл корневой SchemeShard | откате SS |
| `I18` | сколько тенантной стороны увидел прогон | — (покрытие) |
| **`I19`** | восстановленный SchemeShard ничего не доигрывает живым шардам | **откате SS** |

`I4`/`I5`/`I6` (тег `corruption`) — предсказатели **тихой порчи данных**,
остальные дают потери и сирот. Смотреть надо в первую очередь их.

Важная деталь, заложенная в `I4`: Hive чинит свой счётчик сам при загрузке —
`nextTabletId = Max(maxTabletId + 1, NextTabletId)`
(`ydb/core/mind/hive/tx__load_everything.cpp:891`). Он защищён от таблеток,
которые сам помнит, но **не** от тех, что помнит только SchemeShard. Поэтому
ценность именно в сквозной проверке.

Проверки объявляют требования через `needs`. Нет леджера — `I8`/`I12`/`I14`
помечаются `SKIP` с причиной, а не падают. Одна и та же команда работает на
стенде и на проде.

#### Тенантные таблетки: бэкапов нет

`ITablet::NeedBackup` возвращает false при выставленном `TenantPathId`, то есть
тенантные SchemeShard, Hive, координаторы и медиаторы **не бэкапятся вообще**.
Откат кластерной таблетки откатывает одну сторону ссылки, а тенантная сторона
продолжает жить с новым значением.

Критичнее всего раздача tablet id. Корневой Hive — аллокатор: тенантный Hive
просит диапазон (`TEvRequestTabletIdSequence`), корневой пишет выдачу в
`Sequences`/`TabletOwners`, тенантный сохраняет диапазон в своей (небэкапируемой)
БД. Откат корневого стирает запись — диапазон уходит второй раз, два Hive
чеканят одинаковые id. Встроенной починки нет: единственная ресинхронизация
идёт в обратную сторону (`TEvRequestTabletOwners`: тенант спрашивает корневого,
однократно, под флагом `TabletOwnersSynced`).

Отсюда третий источник состояния — **живой кластер**. Тенантные таблетки как раз
те, которых откат не касался, поэтому их надо просто прочитать:
`--mon-endpoint http://host:8765`. Список тенантных Hive извлекается из бэкапа
корневого SchemeShard (`SubDomains` + `SubDomainShards` + `Shards`), читаются они
через `/viewer/json/hiveinfo`.

Без `--mon-endpoint` картина выглядит **лучше**, чем есть: `I4` скажет
«аллокатор выше всех ссылок», просто не увидев тенантных id. Поэтому есть `I18`,
который явно печатает, сколько тенантной стороны прогон не посмотрел.

#### Пространство идентификаторов Hive

Аллокатор считает не полные tablet id, а «unique part» — низкие 44 бита
(`ydb/core/base/tabletid.h`). `State[NextTabletId]`, `Sequences` и `TabletOwners`
— в этом пространстве, `Tablet.ID` и внешние ссылки — в полном. У
`72075186224037888` unique part равен `0x10000`. Всё пространство —
`[0x10000, 0x800000)`, дальше зарезервированное окно.

#### Про измерение свежести (`I11`, `I14`)

Таймстамп в имени каталога бэкапа — **не** мера свежести данных: он говорит,
когда начался снапшот. Бэкап не снимается по таймеру, changelog продолжает
принимать коммиты, и новый снапшот делается только когда changelog перерастает
предыдущий. Каталог с именем `11:00` спокойно может содержать состояние на
`12:00`.

Коммиты changelog несут `step` таблетки, а не время
(`flat_executor_backup.cpp`), и степы разных таблеток несопоставимы. Поэтому
`I11` меряет свежесть по **mtime файла `changelog.json`**, а имя каталога
показывает только как нижнюю границу. mtime — метаданные ФС: переживает
`rsync -a` и `scp -p`, обнуляется обычным `scp -r`. Здоровый кластер и копия с
потерянными временами дают одинаковую картину (нулевую разбежку) и по файлам
неотличимы, поэтому чекер не гадает, а печатает оговорку рядом с вердиктом.

`I14` даёт точный ответ на стенде: датирует состояние каждой таблетки по
леджеру — самой поздней операции, следы которой в ней ещё видны.

### Режим doctor

`--doctor` строит план починки, `--doctor-out DIR` применяет его к копии,
`--in-place` — к оригиналу.

Правка применяется **дописыванием коммита в `changelog.json`**, а не
редактированием снапшота: при restore changelog проигрывается поверх снапшота,
поэтому правка в снапшоте была бы затёрта. Следствия: файлы снапшота и
`manifest.json` не тронуты, их контрольные суммы остаются валидными
(восстанавливаться можно **без** Skip Checksum Validation), а прежние значения
сохраняются в changelog выше по файлу. Restore это принимает — строка должна
быть JSON-объектом с `data_changes`, поле `step` не обязательно, changelog по
контрольной сумме не проверяется (`TTxUploadChangelog`,
`flat_executor_recovery.cpp`).

Чинятся все счётчики идентификаторов: `I4`/`I15` (+`I12`), `I5`, `I6`, `I7`,
`I10`. Запас для tablet id кратен `MaxRequestSequenceSize` (1 000 000): выданный
тенанту диапазон может быть использован частично, и его хвост offline не виден.
Плюс `I19` — но только с `--mon-endpoint`: см. «Что чинит doctor» ниже.
Ссылочные находки (`I1`, `I2`, `I3`, `I8`) не чинятся — забытый объект нельзя
выдумать обратно в файл; для каждой печатается, что делать в кластере.

Проверено end-to-end на S1: было 2 CRITICAL — стало 0, `I1` честно остался.

### Нагрузка

| генератор | что делает | целевой rate |
|---|---|---|
| `ddl_churn` (G1) | create/drop таблиц → SS → Hive → BSC | 2.2 create/s, 1.2 drop/s |
| `restart_churn` (G2) | рестарты случайных таблеток | 6.0/s |
| `bsc_config` (G4) | read-only config-запросы к BSC | 0.04/s |
| `register_node` (G5) | регистрация фейковых узлов (был раньше) | — |

`ddl_churn` после создания резолвит `PathId` и `DatashardId` через
`/viewer/json/describe` и пишет их в леджер — именно эти сквозные ссылки потом
сравнивает чекер.

`bsc_config` безопасен: **любой** `TEvControllerConfigRequest` исполняется через
`TTxConfigCmd` независимо от того, читают его команды или пишут
(`ydb/core/mind/bscontroller/config_cmd.cpp:468`). Поэтому read-only запрос даёт
нужный tx-rate, не трогая топологию хранилища — что критично, раз рядом идут
намеренные восстановления.

**G3 (метрическое давление на Hive) намеренно не реализован.** Период отправки
метрик — константа времени компиляции, единственный рычаг — число живых
таблеток, а им уже управляет `ddl_churn` через `PARTITIONS`.

## 4. Что дальше

1. **Сценарий S1 (откат Hive)** — самый показательный. Процедура: прогреть
   кластер → дождаться снапшота (точка `T0`, сохранить копию каталога) → дать
   поработать 5–15 мин (`T1`) → перевести Hive в RECOVERY → восстановить копию
   `T0` → вернуть в нормальный режим → прогнать чекер. Ожидаются `I1` и `I4`.
2. **S2 (откат SchemeShard)** — ожидаются `I2` и `I6`.
3. **S3 (откат BSController)** — ожидаются `I3` и `I5`; самый опасный.
4. **S4 (все три из разных точек)** — проверка общего правила:

   > после восстановления каждый счётчик последовательности должен быть выставлен
   > в `max(значение, встречающееся где-либо в кластере или в леджере) + запас`.

   Правило превращает тихую порчу (`I4`/`I5`/`I6`) в явные потери
   (`I1`/`I2`/`I3`), которые лечатся реконсиляцией.

### Обходы, которые надо проверить тестом

- **Правка счётчиков в бэкапе перед restore** — автоматизирована режимом
  `--doctor` (см. выше). Ручной путь через редактирование снапшота и
  **Skip Checksum Validation** тоже работает, но doctor предпочтительнее:
  он дописывает коммит в changelog, поэтому контрольные суммы снапшота остаются
  валидными. `I9`/`I10` затем проверяют, что правка не сломала внутреннюю
  согласованность.
- **Пересоздание потерянных шардов с тем же id.** `TEvCreateTablet` имеет поле
  `TabletID` (`ydb/core/protos/hive.proto`, field 22), так что таблетку можно
  вернуть в Hive под прежним идентификатором, сохранив ссылку из SchemeShard.
- **Удаление сирот** по разнице `Hive.Tablet(owner=SS) \ SS.Shards`.

## 5. Что вскрылось на живом слайсе

Прогон против реального кластера (3 хоста, `mirror-3-dc`, база `testdb`) нашёл
шесть дефектов, которые синтетика пропускала. Ни один не был виден на фикстурах.

1. **Каталог называется `bscontroller`, а не `bs_controller`.**
   `ToSnakeCaseDense` не разбивает подряд идущие заглавные. Чекер просто не
   находил бэкап BSController.

2. **`NextTabletId` — это unique part, а не полный tablet id.**
   Аллокатор Hive считает низкие 44 бита (`MakeTabletID(fromHive, uniqPart)`).
   На реальном бэкапе `NextTabletId` = 66546, а ссылки — `72075186224037888`.
   Прежний код пометил бы под угрозой **каждую** таблетку, а doctor поднял бы
   счётчик до ~7.2e16 — за пределы пространства `[0x10000, 0x800000)`, сломав
   выдачу id совсем.

3. **Changelog не обязан быть валидным UTF-8.** `Shards.PartitionConfig`
   объявлен `Utf8` (в схеме рядом стоит комментарий `// TPartitionConfig,
   String?`), а хранит сериализованный protobuf; writer пишет `Utf8` сырьём, и
   сырые байты попадают внутрь JSON-строк. Ридер теперь декодирует с
   `surrogateescape` — структура JSON при этом разбирается полностью.

4. **`Sequences` хранит два разных вида строк.** `OwnerId = 0` — собственный
   свободный диапазон, `Next` в нём живой. `OwnerId != 0` — **запись о выдаче**
   тенантному Hive, её `Next` это слепок на момент выдачи. Прежний предикат
   считал выданный диапазон источником аллокации и выдал 10 CRITICAL на
   здоровом кластере. Плюс `End` — исключающий.

5. **Таблетки базы обслуживает её собственный Hive.** Реальность: корневой Hive
   знал ровно **одну** таблетку — Hive базы `testdb`; её SchemeShard, три
   координатора и три медиатора живут в тенантном Hive. `I1` считал их
   потерянными (9 ERROR), `I16` писал «база не поднимется». Правильное
   утверждение: в корневом Hive обязана быть только сама таблетка-Hive базы.

6. **`SharedHiveId` хранит `InvalidTabletId` (2⁶⁴−1), а не 0**, и у корневого
   домена нет строк в `SubDomainShards` — из-за этого `/Root` считался базой.

Отдельно, без исправления в коде, но с предупреждением: **генерации
перезапускаются при переформатировании дисков**. На слайсе рядом лежали бэкапы
Hive с `g4`/`g5` от мая и `g2` от сегодня. Документированное правило «максимальная
генерация» выбирает майский — от давно мёртвой инкарнации кластера. Загрузчик
теперь печатает note, когда выбранный по генерации бэкап не самый свежий по
времени, и предлагает указать путь явно через `--tablet`.

Итог: на здоровом кластере было 12 CRITICAL + 9 ERROR, стало 0 + 0. С
`--mon-endpoint` тенантный Hive находится автоматически из бэкапа корневого
SchemeShard, читаются его 97 живых таблеток, и `I15` подтверждает запас
аллокатора.

## 6. Прогон восстановления на слайсе

`slice/backup_restore_loop.sh` автоматизирует весь цикл на baremetal-кластере:
нагрузка → устаревшая обрезанная копия → проверка без ledger → doctor →
RECOVERY → restore → возврат в штатный режим → проверка после → подтверждение,
что нагрузка жива. Подробности в `slice/README.md`.

Сценарий подтверждён на слайсе: итерации подряд, восстановление SchemeShard из
копии, отставшей на 30–150 с и обрезанной на 16–48 КиБ. Пример итога:

```
ITER     STALE  TRUNC  RESTORE   WORKL  FINDINGS  before -> after
iter-01  90s    16K    success   84     I1:E134 I2:E466 I6:C88 I13:W1 -> I1:E134 I2:E468
```

Читать надо именно эту строку, а не счётчики текстового отчёта: он обрезает
каждую проверку на 20 находках, поэтому итерации с очень разной степенью
расхождения выглядят одинаково (везде «21 critical, 42 error»). Реальные суммы
берутся из JSON.

Что этот прогон показал:

- **doctor закрывает весь класс тихой порчи.** До восстановления `I6` кричал
  «`NextShardIdx` = 100, а Hive держит индексы до 235» — то есть SchemeShard
  переиздал бы занятые ShardIdx, и `TxCreateTablet` (идемпотентный по
  `(OwnerId, OwnerIdx)`) отдал бы новому объекту чужую живую таблетку. После
  подъёма счётчика — ноль critical.
- **Ссылочные ошибки остаются и это правильно.** 42 ERROR — `I1`/`I2`: объекты,
  созданные после точки бэкапа. Восстановленная таблетка о них не знает, Hive их
  таблетки ещё держит. В файле бэкапа это не чинится.
- **Кластер и нагрузка переживают цикл**: `healthcheck GOOD`, база `GOOD`, все 9
  слотов, нагрузка продолжает создавать и удалять таблицы после реконсиляции
  своего списка.

### Сироты накапливаются от восстановления к восстановлению

Видно только при повторных циклах: `I2` не возвращается к исходному уровню.
После двух прогонов на стенде корневой Hive держал **1350** таблеток, тогда как
SchemeShard знал **429** таблиц по 2 партиции — то есть около **480** таблеток
живут впустую. Каждое восстановление бросает всё, что создано после точки
бэкапа: Hive их держит, SchemeShard на них не ссылается, а GC идёт от
SchemeShard и потому до них не доходит.

Вывод для инструкции по восстановлению: удаление сирот в Hive — обязательный
шаг, а не факультативная уборка. Без него кластер деградирует с каждым циклом.

### Ещё два бага, найденные этим прогоном

7. **`prev_sha256`: у changelog есть цепочка контрольных сумм.** Каждая строка
   несёт sha256 всего содержимого до неё, и restore её проверяет
   (`flat_executor_recovery.cpp`). Дописанный doctor'ом коммит без этого поля
   был отвергнут — Dry Run вернул «Changelog line is missing 'prev_sha256'
   field». Мой ридер молчал, потому что игнорирует незнакомые поля. Теперь
   doctor продолжает цепочку.

8. **Коммит после обрыва недостижим.** Реплей — и мой, и `TTxUploadChangelog` —
   останавливается на первой неразбираемой строке. Дописывать починку **после**
   обрезанного хвоста бессмысленно: на обрезанном бэкапе ремонт молча не
   срабатывал. Теперь doctor отбрасывает неразбираемые записи с конца (restore
   их всё равно не применил бы) и печатает, сколько отбросил.

Оба нашлись только потому, что бэкап действительно восстанавливали. Dry Run
отработал ровно как обещает документация — стоит всегда гонять его первым.

### Баги #9 и #10: восстановленный SchemeShard доигрывает операции

Природа у обоих одна. Строка `TxInFlightV2` живёт ровно до конца операции —
завершившаяся операция стирает её сама. Значит **любая строка, пережившая реплей
снапшота с changelog, это операция, которую восстановленный SchemeShard
продолжит** — обращаясь к шардам, у которых она давно доиграна. Разница между
#9 и #10 в том, кто от этого падает.

9. **`TxCreateTable` в `ConfigureParts` кладёт даташарды в цикл рестартов.**

   На слайсе бэкап поймал операцию `281474976721557` (path 238, ShardIdx
   401/402 → таблетки `72075186224039279` и `72075186224039280`). После
   восстановления SchemeShard переотправил им предложение создать таблицу.
   Даташарды её уже создали и txId забыли, поэтому каждая загрузка таблетки
   упирается в:

   ```
   check_scheme_tx_unit.cpp:425: Condition violated:
       `!DataShard.GetUserTables().contains(tableId)'
   ```

   Ни один из имеющихся фильтров не срабатывает: `TSchemeOpSeqNo` отбрасывает
   только *более старое поколение*, а у восстановленного SchemeShard поколение
   новее; `Pipeline::FindOp`/`FindSchemaTx` знают лишь операции *в полёте*, а эта
   завершена и вычищена. `Y_ENSURE` бросает `yexception`, так что умирает
   таблетка, а не узел — даташард перезапускается бесконечно.

10. **BlockStore/FileStore в `ConfigureParts` кладёт весь узел SchemeShard.**

    Радиус хуже, чем у #9, и это основной профиль прода
    (`TTxBlockStoreConfigResult` — 1.19 tx/s).

    `TConfigureParts` шлёт волюму `TEvUpdateVolumeConfig` с версией из своей БД.
    Живой волюм держит `NextVolumeConfigVersion` в персистентной мете
    (`volume_actor_loadstate.cpp:200`) и отвечает по правилу
    (`volume_actor_updateconfig.cpp:168`):

    | версия из SchemeShard | ответ волюма |
    |---|---|
    | больше применённой | применить, `OK` |
    | равна применённой | `OK` сразу — повтор безопасен |
    | меньше применённой | **`ERROR_BAD_VERSION`** |

    Третий вариант SchemeShard считает невозможным:

    ```cpp
    // Schemeshard never sends invalid or outdated configs
    Y_VERIFY_S(status == NKikimrBlockStore::OK ||
               status == NKikimrBlockStore::ERROR_UPDATE_IN_PROGRESS, ...);
    ```

    `schemeshard__operation_common_bsv.cpp:33` — общий код для create и alter
    волюма; дословно то же самое в `schemeshard__operation_create_fs.cpp:54` и
    `schemeshard__operation_alter_fs.cpp:53`. `Y_VERIFY_S` — это `Panic()`
    `[[noreturn]]`, то есть **abort всего процесса узла**, а не смерть таблетки.
    После рестарта операция всё ещё в `ConfigureParts`, SchemeShard шлёт ту же
    версию снова — цикл падений контрольного слоя.

    Чтобы это случилось, достаточно **одного** alter после точки бэкапа:
    восстановленный SchemeShard считает следующую версию от своей откатившейся
    (`alter_bsv` берёт `volume->AlterVersion + 1`), а волюм уже дальше.
    Равенство безопасно.

    Список допустимых статусов у SchemeShard устроен ровно наоборот к
    реальности: `ERROR_UPDATE_IN_PROGRESS` в непроверочном коде NBS не отдаёт
    никто, а единственный реально отдаваемый ненулевой статус —
    `ERROR_BAD_VERSION` — как раз и ведёт к аборту.

    Тестами не ловится: `TFakeBlockStoreVolume` и `TFakeFileStore`
    (`ut_helpers/test_env.cpp:80,165`) отвечают `OK` безусловно.

    Попутно нашлась соседняя ветка. In-tree Direct-партиция
    (`ydb/core/nbs/cloud/blockstore/libs/storage/partition_direct/partition_direct_actor.cpp`)
    при ошибке отвечает статусом `ERROR` **без `TxId` и `Origin`**;
    `volume_actor.cpp:229` не находит по txId свой запрос, пишет
    `LOG_WARN "for unknown txId"` и молча его роняет. SchemeShard не получает
    ответа вообще и висит в `ConfigureParts` навсегда, а выставленный
    `AlterData` заставляет любой следующий alter падать с «There's another alter
    in flight». Проверки версии там нет вовсе, так что откат конфига
    применяется молча.

**Что теперь проверяет `I19`.** Два независимых предиката:

- *По файлам, без кластера.* Каждая строка `TxInFlightV2`, пережившая реплей,
  печатается с типом операции, состоянием, полным путём и **таблетками**
  (`TxShardsV2` → `Shards`). Состояния, которые шлют сообщения шардам
  (`CreateParts`, `ConfigureParts`, `DropParts`, `DeleteParts`) — CRITICAL;
  `Done`/`Aborted` — WARNING (утечка строки, но доигрывать нечего). Для типов
  BlockStore/FileStore в `ConfigureParts` в текст добавляется, чем именно это
  кончится.
- *Против живого кластера (`--mon-endpoint`).* `BlockStoreVolumes.AlterVersion`
  и `FileStoreInfos.Version` из бэкапа сравниваются с версией из
  `/viewer/json/describe`. Меньше живой — CRITICAL: «restore rolls /Root/vol-42
  back from version 7 to 5». Равно — безопасно. Если в бэкапе есть строка
  alter'а, сравнивается именно её версия: это то, что уйдёт в `ConfigureParts`.

Без `--mon-endpoint` второй предикат не молчит, а печатает WARNING со
счётчиком непроверенных объектов — молчание здесь выглядело бы как «всё
хорошо».

**Что чинит doctor.** Обе половины ремонта требуют `--mon-endpoint`, и это не
недоделка: offline нужного факта в бэкапе нет. Файл говорит «операция в полёте»
одинаково и когда шарды её уже доиграли, и когда до них ничего не дошло, —
различает эти случаи только живой кластер. Без него `I19` попадает в
`unrepairable` с guidance.

- *Откатившаяся версия конфига* (#10). `AlterVersion`/`Version` поднимается
  **ровно до живой**. Именно `==`, а не `+1`: на равную версию волюм отвечает
  `OK`, ничего не применяя, — операция доигрывается, а устаревшее тело конфига
  из бэкапа до работающего волюма не доходит; `live + 1` был бы уже активным
  откатом данных. Если в бэкапе есть строка альтера, двигаются обе версии
  (`...Alters` = live, база = live − 1): `FinishAlter` делает `++Version` и
  проверяет `Version == AlterVersion`
  (`schemeshard_info_types.h:2894`). Если база уже выше цели, ремонт
  пропускается — понижать закоммиченную версию нельзя.
- *Операция, которую живой кластер уже доиграл* (#9). Доказательство берётся из
  `TDirEntry` в describe целевого пути: `CreateTxId` называет **ту самую**
  транзакцию, `CreateFinished` говорит, что создание дошло до конца, а
  `SchemeshardId`/`PathId` подтверждают, что это тот же объект. Значит шарды
  своё уже сделали, и строка удаляется ровно так, как её удаляет сам SchemeShard
  в `PersistRemoveTx` (`schemeshard_impl.cpp:2986`): строка `TxInFlightV2` плюс
  все строки шардов из `TxShardsV2` / `TxShards` / `MigratedTxShards`.

  Два ограничения на старте восстановленной таблетки делают этот ремонт
  «всё или ничего»:

  | место | что требует |
  |---|---|
  | `schemeshard__init.cpp:4179` | `Y_ABORT_UNLESS(subTxId == operation->Parts.size())` — части операции нумеруются подряд с нуля, значит удалять надо **все части** транзакции |
  | `schemeshard__init.cpp:4364` | `Y_VERIFY_S(txState, "There's shard for unknown Operation")` — осиротевшая строка шарда роняет таблетку, значит удалять надо **все** её строки шардов |

  Загрузиться после этого таблетка сможет: `PathState` не персистится
  (`schemeshard__init.cpp:170`), на `StepCreated` незавершённого create никто не
  ассертит.

Что намеренно **не** удаляется: альтеры (осталась бы висеть строка `...Alters`,
после которой новый alter не примут — «There's another alter in flight»), дропы
(в Hive остались бы таблетки, о которых SchemeShard забыл) и операции, чьего
пути живьём нет — такая могла и не дойти до шардов вовсе. Для операций с
версионируемым конфигом удаление тоже не применяется: их доигрывает ремонт
версии. Всё это уходит в guidance вместе с контролом
`SchemeShardControls.TolerateOrphanedPaths`, которым восстановленная таблетка
выбрасывает такие операции сама.

Реально сгенерированный план для случая #9 (два шарда, одна часть):

```
scheme_shard/TxShardsV2 [ShardIdx=401, TxId=281474976721557, TxPartId=0]: erase row
scheme_shard/TxShardsV2 [ShardIdx=402, TxId=281474976721557, TxPartId=0]: erase row
scheme_shard/TxInFlightV2 [TxId=281474976721557, TxPartId=0]: erase row
```

Удаление пишется тем же способом, что и любая другая правка — коммитом в
`changelog.json` с `"op": "erase"`; `FindOpFromJson` в
`flat_executor_recovery.cpp` принимает `upsert`, `erase` и `replace`, поэтому
контрольные суммы снапшота остаются валидными.

## 7. Найденное в документации

`ydb/docs/ru/core/devops/backup-and-recovery/system-tablet-backup.md`
(строки 94, 125, 264) предписывает `boot_mode: RECOVERY`. В проте поле называется
`BootType` (`ydb/core/protos/bootstrap.proto:59`,
`enum EBootType { NORMAL = 0; RECOVERY = 1; }`), то есть в YAML это
`boot_type: RECOVERY`. Рабочий код использует правильное имя
(`workload/__init__.py`, `_make_bootstrap_selector`). Инструкция из доки в
текущем виде таблетку в RECOVERY не переведёт — доку стоит починить.
