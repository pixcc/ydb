# Проверка консистентности кластерных системных таблеток

Инструмент сравнивает состояния Hive, BSController и SchemeShard между собой и
находит расхождения, возникающие после восстановления одной из таблеток из
устаревшей резервной копии.

Пакет **не зависит ни от чего, кроме стандартной библиотеки Python** — его можно
скопировать на любой хост и запустить там. Ни YDB SDK, ни yatest, ни pytest
не нужны.

## Откуда берётся состояние

Снапшот резервной копии — это готовый логический дамп локальной БД таблетки:
по одному NDJSON-файлу на таблицу. Поэтому чекер читает бэкапы и не требует
ни доступа к работающему кластеру, ни специальных ручек мониторинга.

Поверх снапшота применяется `changelog.json` — иначе всё, что создано после
последнего снапшота, выглядело бы как потерянное.

## Запуск на проде

```bash
# 1. Собрать бэкапы с хостов в одно место (пути — из system_tablet_backup_config)
#    Директория должна сохранять структуру <tablet_type>/<tablet_id>/backup_*/
#    Копируйте с сохранением времён (-p / rsync -a), иначе I11 не сможет
#    измерить свежесть состояний — см. раздел ниже.
rsync -a host1:/tablet/hive          /tmp/backups/
rsync -a host2:/tablet/bscontroller /tmp/backups/
rsync -a host3:/tablet/scheme_shard  /tmp/backups/

# 2. Скопировать этот каталог и запустить
scp -r consistency/ host:/tmp/
python3 -m consistency --backup-root /tmp/backups
```

Если копии лежат в произвольных местах, можно указать их явно:

```bash
python3 -m consistency \
    --tablet hive=/tmp/hive/backup_20251007181003Z_g214_s1222 \
    --tablet scheme_shard=/tmp/ss/backup_20251007180500Z_g88_s901 \
    --tablet bscontroller=/tmp/bsc/backup_20251007180500Z_g12_s340
```

Полезные флаги:

| Флаг | Зачем |
|---|---|
| `--list-checks` | список инвариантов с их требованиями |
| `--only I4 --only I5` | прогнать только указанные проверки |
| `--tag corruption` | только предсказатели порчи данных |
| `--mon-endpoint URL` | прочитать тенантные Hive с живого кластера (см. ниже) |
| `--doctor` | план починки счётчиков (см. ниже) |
| `-v` | печатать details каждой находки |
| `--json report.json` | машиночитаемый отчёт |
| `--fail-on warning` | ужесточить код возврата |
| `--skip-checksum-validation` | если бэкап правился руками |
| `--no-changelog` | посмотреть на состояние строго на момент снапшота |

Код возврата: `0` — чисто, `1` — есть находки не ниже `--fail-on`, `2` — не смог
прочитать состояние.

## Что важно понимать про результат

Проверки делятся на два класса, и приоритет у них разный:

- **Ссылочные** (`I1`, `I2`, `I3`) — потери и сироты. Одна таблетка ссылается
  на объект, о котором другая забыла. Неприятно, но лечится реконсиляцией.
- **Монотонность счётчиков** (`I4`, `I5`, `I6`, тег `corruption`) — **тихая
  порча данных**. Откатившийся аллокатор повторно выдаёт идентификатор, который
  всё ещё используется: два объекта получают одни и те же ключи блобов.

`I4`/`I5`/`I6` надо смотреть первыми. Ссылочные находки видны и без инструмента,
а переиспользование идентификатора не проявляется, пока не станет поздно.

## Тенантные таблетки: у них нет бэкапов

`ITablet::NeedBackup` возвращает false, как только у таблетки выставлен
`TenantPathId`. Значит **тенантный SchemeShard, тенантный Hive, координаторы и
медиаторы базы не бэкапятся никогда**. Это и создаёт асимметрию: восстановление
кластерной таблетки откатывает одну сторону ссылки, а тенантная сторона
продолжает работать с новым значением.

Самое опасное — раздача tablet id. Корневой Hive является аллокатором: тенантный
Hive просит у него диапазон (`TEvRequestTabletIdSequence`), корневой записывает
выдачу в `Sequences`/`TabletOwners` и отвечает диапазоном, а тенантный сохраняет
его **в своей БД, у которой бэкапа нет**. Откат корневого Hive стирает запись о
выдаче — и тот же диапазон уходит второй раз. Два Hive начинают чеканить
одинаковые id.

Само это не чинится. Единственная существующая ресинхронизация идёт в обратную
сторону: `TEvRequestTabletOwners` — это *тенантный* Hive спрашивает у *корневого*,
какие диапазоны корневой за ним помнит, и делается это один раз под флагом
`TabletOwnersSynced` в состоянии тенанта (`tx__tablet_owners_reply.cpp`).

Поэтому тенантную сторону надо читать с **живого кластера** — она как раз та,
которую не откатывали:

```bash
python3 -m consistency --backup-root /tmp/backups --mon-endpoint http://host:8765
```

Список тенантных Hive берётся из бэкапа корневого SchemeShard
(`SubDomains` + `SubDomainShards` + `Shards`), читаются они через
`/viewer/json/hiveinfo?hive_id=...`. Отдельный Hive можно назвать явно:
`--tenant-hive <tablet_id>`.

| проверка | что утверждает |
|---|---|
| `I15` | корневой Hive не выдаст повторно id, который уже принадлежит тенантному Hive (нужен `--mon-endpoint`) |
| `I16` | у каждой базы, известной корневому SchemeShard, все её таблетки известны Hive |
| `I17` | Hive не держит таблетки баз, о которых корневой SchemeShard забыл |
| `I18` | сколько тенантной стороны этот прогон вообще увидел |

`I18` существует потому, что без `--mon-endpoint` картина выглядит **лучше, чем
она есть**: `I4` честно скажет «аллокатор выше всех ссылок», просто потому что
тенантных id он не видел. Молчание в такой ситуации хуже предупреждения.

Недоступный тенантный Hive — тоже пробел в покрытии, а не «всё хорошо»: `I15`
печатает WARNING со списком непрочитанных.

## Что восстановленная таблетка сделает дальше (`I19`)

Остальные проверки спрашивают, согласовано ли восстановленное состояние само с
собой. `I19` спрашивает другое: что таблетка **сделает**, когда снова начнёт
работать.

Строка `TxInFlightV2` живёт ровно до конца операции — завершившаяся стирает её
сама. Поэтому любая строка, пережившая реплей, это операция, которую
восстановленный SchemeShard продолжит, обращаясь к шардам, у которых она давно
доиграна. Наблюдалось дважды:

- `TxCreateTable` в `ConfigureParts` → даташард падает на
  `Y_ENSURE(!DataShard.GetUserTables().contains(tableId))`
  (`check_scheme_tx_unit.cpp:425`) и перезапускается бесконечно. Умирает
  таблетка;
- `TxCreate/AlterBlockStoreVolume` и то же для FileStore в `ConfigureParts` →
  волюм отвечает `ERROR_BAD_VERSION` на устаревший конфиг, а SchemeShard считает
  такой ответ невозможным:
  `Y_VERIFY_S(status == OK || status == ERROR_UPDATE_IN_PROGRESS, ...)`
  (`schemeshard__operation_common_bsv.cpp:33`). `Y_VERIFY_S` — это abort
  процесса, то есть умирает **узел**, а после рестарта операция всё ещё в
  `ConfigureParts`.

Отсюда два предиката:

| предикат | нужен кластер | вывод |
|---|---|---|
| выжившая строка `TxInFlightV2` | нет | тип операции, состояние, путь и таблетки (`TxShardsV2` → `Shards`) |
| откат версии волюма | да, `--mon-endpoint` | `AlterVersion`/`Version` из бэкапа против живой |

Версия сравнивается так: **меньше живой — CRITICAL**, потому что волюм откажет и
уронит узел; равна — безопасно, волюм отвечает `OK` на конфиг, который уже
применил. Если в бэкапе лежит строка alter'а, сравнивается её версия — именно
она уйдёт в `ConfigureParts`.

Живые версии читаются через `/viewer/json/describe?path=...` для тех путей,
которые нашлись в бэкапе SchemeShard (`BlockStoreVolumes`, `FileStoreInfos`);
удалённые пути пропускаются. Без `--mon-endpoint` второй предикат печатает
WARNING со счётчиком непроверенных — по той же причине, по которой существует
`I18`.

## Насколько состояния разъехались по времени (`I11`, `I14`)

Здесь важно понимать ограничение формата.

**Таймстамп в имени каталога бэкапа — это НЕ мера свежести данных.** Он говорит,
когда *начался снапшот*. Бэкап не снимается по таймеру: changelog продолжает
принимать коммиты сколько угодно долго, а новый снапшот делается только когда
changelog перерастает предыдущий. Поэтому каталог с именем `11:00` может
содержать состояние на `12:00`, и сравнивать имена каталогов между таблетками
бессмысленно.

Коммиты changelog несут `step` таблетки, а не время, и степы разных таблеток
несопоставимы. Остаётся единственный сигнал — **mtime файла `changelog.json`**,
то есть когда таблетка последний раз записала изменение. Его и использует `I11`.
Это метаданные ФС: они переживают `rsync -a` и `scp -p`, но обнуляются обычным
`scp -r`. Здоровый кластер (снапшоты сняты в разное время, changelog у всех
свежий) и копия с потерянными временами выглядят **одинаково** — нулевой
разбежкой. Отличить их по файлам нельзя, поэтому чекер не гадает, а всегда
печатает оговорку рядом с вердиктом.

`I14` даёт точный ответ, но только на стенде: он датирует состояние каждой
таблетки по леджеру — самой поздней операции, следы которой в ней ещё видны.
Это не зависит от того, как копировали файлы.

## Проверки, требующие леджера

`I8`, `I12` и `I14` используют журнал операций нагрузочного теста. На проде его
нет, поэтому они помечаются как `SKIP` с явной причиной, а не падают. Это и есть
смысл механизма требований: одна и та же команда работает и на стенде, и на
проде, честно сообщая, что она не смогла проверить.

## Режим doctor: починить то, что чинится

```bash
# 1. посмотреть план (ничего не пишет)
python3 -m consistency --backup-root /tmp/backups --doctor

# 2. применить к копии (рекомендуется)
python3 -m consistency --backup-root /tmp/backups --doctor --doctor-out /tmp/repaired

# 3. перепроверить и восстанавливаться из /tmp/repaired
python3 -m consistency --backup-root /tmp/repaired
```

`--in-place` правит исходные каталоги вместо копии.

**Как применяется правка.** Не редактированием снапшота: при восстановлении
поверх снапшота проигрывается changelog, поэтому правка в снапшоте была бы
затёрта более поздним коммитом той же строки. Вместо этого doctor **дописывает
коммит в `changelog.json`**. Это работает по семантике «последняя запись
побеждает» и даёт два следствия:

- файлы снапшота и `manifest.json` не тронуты, их контрольные суммы остаются
  валидными — восстанавливаться можно **без** Skip Checksum Validation;
- ничего не разрушено: прежние значения остаются в changelog выше по файлу.

Restore это принимает: строка changelog должна быть JSON-объектом с
`data_changes` и/или `schema_changes` (`TTxUploadChangelog` в
`flat_executor_recovery.cpp`), поле `step` не обязательно, а сам changelog на
пути восстановления не проверяется по контрольной сумме.

**Что doctor чинит:** `I4`/`I15` (+`I12`), `I5`, `I6`, `I7`, `I10` — то есть все
счётчики идентификаторов. Каждый поднимается выше максимума, встречающегося
где-либо: в загруженных бэкапах, в леджере и в живом чтении тенантных Hive.

Плюс `I19` — но только вместе с `--mon-endpoint`. Здесь чинится не счётчик, а
то, что восстановленный SchemeShard **сделает дальше**, и обе половины ремонта
опираются на живой кластер, потому что offline нужного факта просто нет.

- *Откатившаяся версия конфига* (`TxCreateBlockStoreVolume` и родня). Версия
  поднимается **ровно до живой**: на равную версию волюм отвечает `OK`, ничего
  не применяя, — операция доигрывается, а устаревшее тело конфига из бэкапа до
  работающего волюма не доходит. На единицу выше было бы уже откатом данных.
  Если в бэкапе есть строка альтера, обе версии двигаются вместе: `FinishAlter`
  делает `++Version` и проверяет равенство с версией альтера.
- *Операция, которую живой кластер уже доиграл*. Доказательство — describe
  целевого пути: `CreateTxId` называет ту самую транзакцию, а `CreateFinished`
  говорит, что создание дошло до конца. Значит шарды своё сделали, и строка
  операции удаляется ровно так, как её удаляет сам SchemeShard
  (`PersistRemoveTx`): сама строка плюс все строки шардов. Два ограничения
  жёсткие: операция удаляется **целиком, всеми частями** (на старте стоит
  `Y_ABORT_UNLESS(subTxId == operation->Parts.size())`) и **вместе со всеми**
  строками шардов (осиротевшая строка шарда роняет таблетку: `Y_VERIFY_S(txState,
  "There's shard for unknown Operation")`).

Что здесь намеренно **не** трогается: альтеры и дропы. Удалить альтер — оставить
висеть строку `...Alters`, после которой новый альтер уже не примут; удалить
дроп — оставить в Hive таблетки, о которых SchemeShard забыл. А операция, чьего
пути живьём нет, могла и не дойти до шардов вовсе. Для всего этого печатается
guidance, включая контрол `SchemeShardControls.TolerateOrphanedPaths`, которым
восстановленная таблетка выбрасывает такие операции сама.

Запас для tablet id взят не с потолка. Диапазон, уже выданный тенантному Hive,
может быть использован лишь частично, и его неиспользованный хвост offline не
виден. Максимальный размер выдачи — `MaxRequestSequenceSize` (по умолчанию
1 000 000), поэтому запас берётся кратным ему. Всё пространство — это только
`[0x10000, 0x800000)`, так что запас не бесплатен: если поднятие упирается в
зарезервированное окно, doctor отказывается и говорит, что нужен человек.

**Что doctor не чинит и честно об этом говорит:** ссылочные находки
(`I1`, `I2`, `I3`, `I8`) и остаток `I19`. Забытый одной таблеткой объект нельзя
выдумать обратно в файл бэкапа — это реконсиляция в работающем кластере. Для
каждой такой находки печатается, что именно надо сделать.

Пример вывода:

```
DOCTOR

applied:
  I4
      hive/State [Key=0]: Value 72075186224037889 -> 72075186225086466
        reason: raise NextTabletId above max referenced tablet id 72075186224037889 plus a 1048576 gap

resolved by the repairs above:
  I12  covered by repairing I4

not repairable by editing the backup:
  I1  1 finding(s)
      SchemeShard still knows the tablet ids. Re-create the missing tablets in Hive
      with TEvCreateTablet carrying the original TabletID (hive.proto field 22)...
```

Смысл ровно тот, что нужен при восстановлении: правка счётчиков превращает
**тихую порчу данных** в **явную потерю**, которая уже лечится реконсиляцией.

### Осторожно: пространство идентификаторов

Аллокатор Hive считает **не полные tablet id**, а их «unique part» — низкие
44 бита (`MakeTabletID(fromHive, uniqPart)` в `ydb/core/base/tabletid.h`).
`State[NextTabletId]`, `Sequences` и `TabletOwners` живут в этом пространстве,
а `Tablet.ID` и все ссылки извне — в полном. Сравнивать их напрямую нельзя:
у `72075186224037888` unique part равен `0x10000`. Всё, что касается аллокатора,
в коде проходит через `views.uniq_part()`.

### Как добавить свой ремонт

```python
from .doctor import Edit, repair

@repair("I15")
def fix_something(state):
    yield Edit(tablet_type=HIVE, table="State", key={"Key": 7},
               values={"Value": 42}, current={"Value": 1},
               reason="почему именно так")
```

`op="erase"` удаляет строку целиком (`values` тогда пустой) — restore понимает
`upsert`, `erase` и `replace` одинаково.

Если у проверки ремонта нет, добавьте строку в `doctor.GUIDANCE` — что делать
руками. Если ремонт читает таблицы, которых сама проверка не объявляет,
допишите их в `doctor.REQUIRED_TABLES`.

## Как добавить свой инвариант

Один декорированный генератор в `checks/`:

```python
from ..model import HIVE, SCHEME_SHARD, error
from ..registry import check

@check(
    id="I15",
    title="Короткая формулировка утверждения",
    needs={SCHEME_SHARD: ["Shards"], HIVE: ["Tablet"]},
    tags=("refs",),
)
def my_invariant(state):
    """Чем ломается и почему это важно."""
    for ...:
        yield error("что не так", tablet_id=..., path_id=...)
```

и одна строка в `checks/__init__.py`.

`needs` работает сразу в двух ролях: объявляет требования (при отсутствии среза
проверка пропускается, а не падает) и говорит загрузчику, какие таблицы читать —
чтобы прогон на проде не тянул в память многогигабайтные дампы ради проверок,
которые всё равно отфильтрованы.

Знание схем локальных БД собрано в `views.py` — это единственное место,
завязанное на C++-схемы Hive / SchemeShard / BSController.
