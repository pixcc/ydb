# Прогон восстановления из устаревшего бэкапа на слайсе

Скрипты для повторяемого эксперимента на baremetal-кластере: гоняем нагрузку,
восстанавливаем кластерную системную таблетку из **устаревшего и обрезанного**
бэкапа и проверяем, что кластер и нагрузка после этого живы.

Всё исполняется **на хосте кластера** — нужны `/Berkanavt`, локальный `ydb` CLI
и `sudo` для работы с каталогом бэкапов.

## Установка

```bash
# чекер отчуждаем и состоит только из stdlib, поэтому просто копируется
rsync -a ydb/tests/stress/system_tablet_backup/consistency  host:~/
scp ydb/tests/stress/system_tablet_backup/slice/*.sh        host:~/
ssh host 'chmod +x ~/backup_restore_loop.sh ~/workload.sh'
```

Проверить, что чекер поднялся (на хосте хватает Python 3.8):

```bash
ssh host 'python3 -m consistency --list-checks | head'
```

## Запуск

```bash
~/backup_restore_loop.sh -n 10                 # десять циклов подряд
~/backup_restore_loop.sh -n 5 -t hive          # то же для Hive
~/backup_restore_loop.sh -n 3 --no-doctor      # без автопочинки, для сравнения
```

| Флаг | Смысл |
|---|---|
| `-n N` | сколько итераций |
| `-t TABLET` | `scheme_shard` (по умолчанию), `hive`, `bscontroller` |
| `-o DIR` | куда складывать артефакты (по умолчанию `~/restore-runs`) |
| `--no-doctor` | восстанавливать без починки — видно, что именно чинит doctor |

Одна итерация занимает ~4 минуты, из них две перезагрузки статической ноды.

## Что делает итерация

1. Проверяет `healthcheck GOOD` и поднимает нагрузку, если не запущена.
2. Копирует текущий бэкап таблетки в сторону — это и есть «устаревшая» копия.
3. Ждёт `staleness` секунд, пока кластер уходит вперёд.
4. Обрезает хвост `changelog.json` — записи, не успевшие доехать.
5. Прогоняет чекер **без ledger** → `report-before.txt` + `.json`.
6. Прогоняет doctor → `repaired/` + `doctor.txt`.
7. Переводит таблетку в `boot_type: RECOVERY`, перезапускает ноду.
8. Dry Run, затем настоящее восстановление.
9. Снимает RECOVERY, перезапускает, ждёт `GOOD`.
10. Прогоняет чекер по свежим бэкапам → `report-after.txt`.
11. Приводит список таблиц нагрузки в соответствие с реальностью и убеждается,
    что нагрузка снова создаёт объекты.

Итерация падает, если кластер не вернулся в `GOOD` или нагрузка не сдвинулась.
Остальные итерации при этом продолжаются.

`staleness` (30/90/150 с) и размер обрезания (0/16/32/48 КиБ) меняются по номеру
итерации, поэтому повторные прогоны попадают в разные случаи.

## Артефакты

`$OUTDIR/iter-NN/`:

| Файл | Что внутри |
|---|---|
| `params.txt` | параметры итерации |
| `stale/` | устаревшая копия до починки |
| `repaired/` | то, что реально восстанавливали |
| `report-before.txt` / `.json` | проверка до восстановления |
| `doctor.txt` | план починки и что осталось на реконсиляцию |
| `dryrun.txt`, `restore.txt` | статусы восстановления |
| `report-after.txt` / `.json` | проверка по свежим бэкапам после |
| `summary.txt` | строка итога |

## Как читать сводку

```
ITER     STALE  TRUNC  RESTORE   WORKL  FINDINGS  before -> after
iter-01  90s    16K    success   82     I1:E22 I2:E22 I6:C37 I13:W1 -> I1:E22 I2:E22
```

`<проверка>:<severity><количество>`. Важно смотреть именно сюда, а не на
текстовый отчёт: он обрезает каждую проверку на 20 находках, и итерации с очень
разной степенью расхождения выглядят одинаково.

Здоровый цикл выглядит так:

- **все `C` исчезают** — doctor поднял счётчики идентификаторов, тихой порчи
  данных не будет;
- **`E` остаются** — это `I1`/`I2`, подлинная потеря: объекты, созданные после
  точки бэкапа, восстановленная таблетка не знает, а Hive их таблетки ещё
  держит. В файле не чинится, лечится реконсиляцией в кластере;
- **`WORKL` больше нуля** — нагрузка пережила восстановление.

Если после итерации остался хоть один `C` — это находка: либо doctor чего-то не
умеет, либо появился новый класс расхождений.

## Если после восстановления таблетки перезапускаются (`I19`)

Так выглядел `iter-01`: SchemeShard поднялся, нагрузка пошла, а два даташарда
крутились в цикле рестартов.

```bash
sudo journalctl -u kikimr -S '13:57' | grep -i 'condition violated'
```

```
check_scheme_tx_unit.cpp:425: Condition violated:
    `!DataShard.GetUserTables().contains(tableId)'
```

Причина — операция, которую бэкап поймал незавершённой. Строка `TxInFlightV2`
стирается только при завершении операции, поэтому восстановленный SchemeShard
продолжает её и переотправляет предложение шардам, у которых таблица давно
создана. `I19` печатает такие операции ещё **до** восстановления, вместе с
таблетками, которые пострадают:

```
I19 CRITICAL operation 281474976721557:0 (TxCreateTable) survived the replay at
    ConfigureParts on /Root/db/table and will be resumed against shards
    401 (tablet 72075186224039279), 402 (tablet 72075186224039280)
```

Для BlockStore/FileStore то же самое кончается хуже: волюм отвечает
`ERROR_BAD_VERSION` на откатившуюся версию конфига, а SchemeShard на этом
статусе делает abort **всего узла**. Чтобы это увидеть заранее, нужен живой
кластер:

```bash
python3 -m consistency --backup-root ~/restore-runs/iter-01/backup \
    --mon-endpoint http://localhost:8765 --only I19
```

Практический вывод для цикла: `I19:C*` в колонке `before` означает, что
восстановление именно этой копии оставит после себя перезапускающиеся таблетки.

Doctor это чинит, но **только с `--mon-endpoint`** — цикл его туда передаёт, так
что в прогоне ремонт работает. Offline тут не обойтись: нужен именно живой
кластер, чтобы отличить операцию, которую шарды уже доиграли, от той, до которой
дело не дошло. Версия волюма поднимается ровно до живой (на равную волюм
отвечает `OK`, ничего не применяя), а завершённая операция удаляется целиком —
строка `TxInFlightV2` всех её частей плюс все строки шардов, — если describe
целевого пути говорит `CreateTxId` = та самая транзакция и `CreateFinished`.
Альтеры, дропы и операции с непрочитанным путём остаются в `unrepairable` с
guidance: их безопасного offline-решения нет.

## Сироты накапливаются от прогона к прогону

Это главное, что видно именно при повторных циклах. `I2` не возвращается к
исходному уровню после восстановления:

```
iter-01  90s   16K  I2:E466 I6:C88  -> I2:E468
iter-02  150s  32K  I2:E616 I6:C148 -> I2:E618
```

Каждое восстановление из устаревшей копии бросает таблетки, созданные после
точки бэкапа: Hive продолжает их держать, SchemeShard на них больше не
ссылается, а сборка мусора идёт от SchemeShard — и потому до них не доходит.
После двух циклов на стенде было так:

```
таблеток в root Hive:            1350
путей в SchemeShard (w_*):        429   (по 2 партиции => ~866 ожидаемых)
```

То есть ~480 таблеток живут впустую, занимая слоты и хранилище.

**Реконсиляция сирот — не уборка по желанию, а обязательный шаг.** Без неё
кластер деградирует от прогона к прогону. Скрипт их намеренно не удаляет:
удаление таблеток необратимо и должно быть осознанным решением. Список берётся
из разности `Hive.Tablet(owner=SchemeShard) \ SchemeShard.Shards` — ровно то, что
печатает `I2` с `-v`.

## Ограничения

- Скрипт рассчитан на слайс, где системные таблетки прибиты к одной ноде
  (`bootstrap_config`). Перезапускается именно она.
- RECOVERY выключает контрол-плейн на время цикла: создание таблиц в этот момент
  падает, это ожидаемо.
- `--no-doctor` оставляет кластер с переиспользуемыми идентификаторами. Так и
  задумано для сравнения, но следующую итерацию стоит гонять уже с doctor.
