Главный ответ о времени без оптимизаций

Теперь есть сопоставимая серия с отдельным процессом сбора счётчиков:
  полностью исходная версия: 16,634 с в среднем (пять прогонов);
  все десять изменений:      11,745 с в среднем (пять прогонов).
Время переноса уменьшилось на 29,39%. CPU двух серверов: 392,576 -> 337,256 CPU-с
(-14,09%, включая сопутствующую фоновую нагрузку). Цена ускорения: p50 фоновой
записи 13,99 -> 18,92 мс; p95 43,47 -> 47,26 мс. Частота записи, напротив,
улучшилась с 380,46 до 399,57/с, длинные стартовые паузы исчезли.
Полностью безопасным для фоновой задержки этот набор пока считать нельзя.

Исходная ревизия: e8700d379b3b9c4fbaf68f36424e6bcf08314fd2, чистый worktree.
Оба узла используют выбранную версию. PDisk SectorMap, 600000 строк, 8 партиций,
8 сканов, 192 КиБ sender buffer, 400 UPSERT/с. Подробности новой серии — в конце.
Два прогона содержат стороннюю I/O-активность хоста и сохранены в результатах.

16,041 с — контроль перед добавлением раннего пробуждения скана. В нём уже
были предыдущие оптимизации. После раннего пробуждения в той же серии было

Десять реализованных изменений

1. Разбор JSON непосредственно из памяти.
   Файлы: library/cpp/json/json_reader.cpp, json_reader.h;
   ydb/core/tx/replication/service/json_change_record.cpp.
   Добавлен ReadJson(TStringBuf, config, callbacks). Репликация использует
   строковый буфер вместо TMemoryInput и обёртки IInputStream. Убирается
   промежуточный потоковый путь; разбор и callbacks остаются общими.
   Отдельного подтверждённого выигрыша полного переноса в доступных данных нет.

2. Преобразование Utf8 без промежуточного копирования в TMemoryPool.
   Файл: ydb/core/tx/replication/service/json_change_record.cpp.
   MakeCellFromJson использует память строки из JsonBody. До уничтожения
   JsonBody ключ получает собственное хранение либо значение сериализуется.
   Отдельного подтверждённого выигрыша полного переноса в доступных данных нет.

3. Числовые значения, помещающиеся внутрь TCell, без выделения в пуле.
   Файл: ydb/core/io_formats/cell_maker/cell_maker.cpp.
   При TCell::CanInline(sizeof(U)) значение создаётся на стеке и копируется
   внутрь TCell. Для остальных типов сохранено выделение в TMemoryPool.
   Отдельного подтверждённого выигрыша полного переноса в доступных данных нет.

4. Повторное использование уже разобранного ключа.
   Файлы: ydb/core/tx/replication/service/json_change_record.cpp, .h.
   Serialize использует сохранённый Key вместо повторного преобразования
   JSON-ключа. При замене тела записи или схемы кеш ключа сбрасывается.
   Отдельного подтверждённого выигрыша полного переноса в доступных данных нет.

5. Передача уже находящихся в памяти записей напрямую отправителю.
   Файлы: ydb/core/change_exchange/change_sender.cpp, .h;
   ydb/core/tx/replication/service/base_table_writer.cpp.
   EnqueueResidentRecords передаёт тела из PendingRecords без лишнего цикла
   RequestRecords/ProcessRecords. Маршрутизация всего входного пакета доступна
   сразу; исходящие пакеты ограничиваются MemLimit, барьер смены схемы сохранён.
   Измерялось совместно с пунктами 6–7; отдельный вклад не выделен.

6. Сохранение offset репликации один раз на split key за транзакцию.
   Файл: ydb/core/tx/datashard/datashard_repl_apply.cpp.
   TReplicationOffsetsBatch собирает последние offsets и записывает их в конце
   транзакции. Проверка offset и дедупликация остаются для каждой строки.
   Данные и итоговый offset фиксируются в одной транзакции.
   Apply здесь означает применение полученных изменений на приёмнике.

7. Выделение диапазона номеров CDC-записей на пакет initial scan.
   Файлы: ydb/core/tx/datashard/cdc_stream_scan.cpp;
   ydb/core/tx/datashard/datashard.cpp, datashard_impl.h.
   AllocateChangeRecordOrder обновляет системное значение один раз на пакет,
   затем номера выдаются из диапазона. Убираются обновления Sys для каждой
   строки. Пропуски строк могут оставлять промежутки в номерах.

   Ранее для совместного набора 5–7 были отмечены:
   - Execute CPU применения на запись: -12,5%;
   - объём redo применения: -7,3%;
   - объём redo скана: -3,4%.
   Это метрики отдельных стадий, не доказательство ускорения полного переноса.
   Относить весь результат отдельно к пункту 6 или 7 нельзя.

8. Исправление двойного учёта резервирования очереди CDC.
   Файлы: ydb/core/tx/datashard/datashard.cpp, datashard_impl.h.
   ChangeQueuePendingCapacity учитывает только ещё не поставленные в очередь
   пакеты. Уже поставленные записи занимают очередь и бюджет скана, но больше
   не учитываются второй раз как ожидающее резервирование.
   Ранее в памяти: перенос 16,15 -> 15,94 с; фоновые UPSERT 371,7 -> 392,1/с;
   p99 151 -> 124 мс. Значимое ускорение полного переноса не установлено.
   В серии на реальных дисках было ухудшение 17,71 -> 31,96 с, включая три
   медленных случая; одновременно ухудшались задержки физического I/O.
   Причинная связь регрессии с кодом не установлена. Универсальная безопасность
   этой правки на основании тех опытов не доказана.

9. Пробуждение initial scan сразу после освобождения очереди.
   Файлы: ydb/core/tx/datashard/cdc_stream_scan.cpp,
   datashard_change_sending.cpp, datashard_impl.h.
   Вместо обязательного повторения через 1 с пакет ждёт в WaitingCdcStreamScans.
   После завершения транзакции удаления записей выполняется проверка свободного
   места и пробуждение. Таймер 1 с оставлен как резервный путь. Лимиты очереди
   при этом не увеличиваются.
   Ранняя серия в памяти, A-B-B-A-B:
     A: 15,888; 16,194 с. Среднее 16,041 с.
     B: 10,408; 10,466; 10,456 с. Среднее 10,444 с.
   Время переноса -34,9%; CPU примерно 324 -> 275 CPU-с (-15%).
   Фоновые UPSERT 393,4 -> 391,8/с; p95 44 -> 53 мс; p99 114 -> 124 мс.
   Среднее число занятых ядер выросло примерно с 20 до 26: работа выполняется
   интенсивнее и заканчивается раньше. Выигрыш времени был большим, но влияние
   на фоновые задержки не позволяет считать оптимизацию безусловно безопасной.
   В той серии данные сверены во всех пяти прогонах; прошли 18 InitialScan тестов.

10. Проверка заполнения очереди до запуска транзакции прогресса скана.
    Файлы: ydb/core/tx/datashard/cdc_stream_scan.cpp;
    ydb/core/tx/datashard/datashard_ut_change_exchange.cpp.
    Для известной таблицы и потока заведомо заблокированный пакет сразу
    переводится в ожидание. Резервирование сохранено, внутри транзакции остаётся
    повторная проверка состояния. Новое утверждение теста проверяет ноль
    завершённых read-only транзакций при полном буфере.
    Серия 26 октября в памяти, A-B-B-A-B:
      A: 11,636; 11,550 с. Среднее 11,593 с.
      B: 10,706; 11,881; 10,581 с. Среднее 11,056 с.
    Пустые транзакции: 1212/1211 -> 0 во всех B; полезные: 1240 во всех A/B.
    Средние CPU двух серверов: 320,68 -> 297,31 CPU-с (-7,29%).
    Однако CV CPU/запись у B = 10,81%; bootstrap-интервал B/A включает отсутствие
    улучшения. Заданная цель >=3% снижения CPU/запись не подтверждена.
    ExecuteCPUTime всех транзакций прогресса: 7,109 -> 6,864 CPU-с. Разница
    0,245 с не объясняет общую разницу процессов в 23,373 CPU-с.
    Все пять полных сверок данных и 18 InitialScan тестов прошли.
    Статус: устранение лишних транзакций подтверждено; эффект всей репликации
    и безопасность для фоновой нагрузки ещё не доказаны.

Что ещё пробовали и что не следует считать сделанной оптимизацией кода

- Увеличение лимита очереди в 4 раза: ранее 15,95 -> 11,58 с, но p99 фоновых
  записей 93 -> 159 мс. Это диагностическая настройка с ухудшением задержек.
- Сравнивались размеры буфера 192 КиБ и 2 МиБ при 8 партициях/сканах. Сохранённых
  численных результатов этого сравнения сейчас нет; цифры не восстановлены.
  Важно: MemLimit отправителя и BatchMaxBytes initial scan — разные ограничения.
- Перевод PDisk в SectorMap исключает физический диск из основного пути хранения;
  это способ изоляции ресурса в эксперименте, не исправление репликации.
- В серии 26 октября сборщик метрик мешал писателям через общий Python-процесс.
  Поэтому её p95/p99 не доказывают безопасность для фоновой нагрузки.
  В новой серии /var/tmp/ydb-repl-full-20261026 выполнены пять переносов каждой
  версии с отдельным процессом monitor.py. Влияние наблюдения стало другим,
  но не нулевым; результаты приведены ниже.

Главное ограничение исходной версии — ожидание очереди: до 13 переносов скана
на таймер 1 с на партицию. После правок максимальная сумма ожиданий на

оно не объясняет всю экономию процессов 55,32 CPU-с. Наибольшая разница
агрегатного CPU — System pool источника; точную функцию ещё нужно найти perf.

При цели 400 фоновых UPSERT/с получено 380,46 -> 399,57/с.
Средние по прогонам p50: 13,99 -> 18,92 мс; p95: 43,47 -> 47,26 мс;
p99: 72,90 -> 71,00 мс. В каждом A — 32 запроса дольше 150 мс, максимум
0,91–0,95 с; в каждом B — ноль, максимум <147 мс. Отказы переполнения очереди:
66–83 -> 0. Окончательных ошибок нет, все записи сверены. SDK — по 11 повторов
на вариант из-за смены схемы при включении репликации.

Среднее число занятых серверных ядер: 23,60 -> 28,71 из 64. RAM >=205 GiB
свободно. PDisk в памяти; vda обычно активен лишь 139–685 мс за перенос.
В run-03 и run-04 была сторонняя запись на vda (0,90/6,16 GB, активное время
8,2/10,4 с). Оба результата сохранены. Не начавшие перенос попытки во время
сборок архивированы отдельно; пользователь попросил ждать завершения сборок.

Новый сборщик не делит GIL с писателями, но его стоимость не нулевая.
В контроле p99 пересекающихся с выгрузкой запросов 62–101 мс против 13–37 мс
вне неё. С прежним сборщиком чистого A/B не было: также изменена частота
проверки завершения с 1 с до 0,25 с. Здесь обе версии измерялись одинаково.

Вывод: ускорение переноса подтверждено на этом стенде; безопасность всего
набора для фоновой задержки не доказана. Есть рост p50, а интервал отношения
p95 допускает регрессию до ~23%. Это нужно отделить от устранённой стартовой
паузы. Все десять правок остаются перечисленными выше; в этой серии новых
изменений серверного кода не сделано.
